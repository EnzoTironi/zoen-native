# Shared incurred-result retention

Part of [agent continuity #327](https://github.com/EnzoTironi/zoen-native/issues/327), using the [existing shared checkpoint](shared-runtime-continuity.md). Enzo owns product direction; Codex root owns this technical implementation. This is accounting/result retention, not activation of public model execution, publication, refunds or complete deployment restore.

## Original result before database work

An authenticated chat Capture binds the frozen request, context, price and response. Before SQL/FDB work, the existing independent anchor writer durably retains its original encrypted bytes and opaque IDs under a content address. Files use the existing private directory, writer ownership, temporary-file/fsync/rename/directory-sync pattern. Exact retries synchronize the same original; they never replace it. These files are inert evidence, not another ledger, provider queue or live admission. No prompt, response text or credential is written in plaintext.

Original staging works before reconciliation, including when another transition is pending or a bank is unavailable. If the host cannot acknowledge this staging, the existing FDB evidence/transfer path is attempted independently. Once the stores are available, `reconcile` derives unfinished work from originals absent from the committed capture inventory, plus that existing FDB fallback queue. No separate completion flag is stored. Completed original files remain retained; automatic retention/GC and production scale remain open work.

The default original-store API stays bounded at 512 files and 512 KiB per record. Its explicit large-record API permits a declared bound up to 64 MiB; chat uses a binary source frame above the old ciphertext threshold. Small source JSON bytes and their addresses remain exact. Chat Capture similarly keeps its original JSON bytes/digest whenever they fit, and otherwise stores a bounded header plus raw provider body. Original ciphertext is retained, never resealed during recovery.

An explicitly signed price profile can now admit the gateway's existing maximum of 16 MiB response bytes. Existing signed profiles and digests do not change; a larger gateway configuration still cannot exceed its authorized price profile. A complete Capture is bounded at 34 MiB, including metadata and output plus the raw body; generic ciphertext/transfer batches allow 64 MiB. Image encoding keeps its own existing 32 MiB limit. FoundationDB reuses the existing 64 KiB immutable evidence chunks and authenticated manifest instead of storing a large value. Reads pipeline at most 16 chunks (1 MiB) inside the caller’s same transaction, checking every chunk and the complete manifest digest.

Apply relay migration `0047_chat_capture_evidence.sql` before running the larger chat profile. PostgreSQL preserves the old 98,304-byte boundary for existing small profiles; larger chat records require the frozen larger profile and matching original claim/admission witness. The independent image ceiling stays 32 MiB. The ciphertext column uses PostgreSQL `EXTERNAL` storage: ordinary durable TOAST values without trying to compress encrypted bytes ([PostgreSQL 16](https://www.postgresql.org/docs/16/storage-toast.html)). The migration broadens storage only; custody and exact request/binding validation remain mandatory.

The coherent capture inventory is bounded at 256 MiB. Ordinary shared transitions reserve one subject and the maximum allowed Capture size for each admitted attempt without a capture. Other activity cannot consume this in-flight capacity. Physical chunks are uploaded before the transaction obtains its read version, so the transaction can observe its new payload. Bulk custody authentication runs before the database transaction and produces an operation-local proof bound to the exact ciphertext and digest. Within the snapshot, capture still checks every physical chunk, the committed ciphertext/root hashes, frozen Binding and original admitted nonce; historical inventory checks those independent commitments without decrypting every prior response again under a database lock. The larger shared capture/reconciliation futures are boxed at the common Runtime entry points so their debug-mode state machines do not enlarge ordinary message call stacks. Ordinary admission transactions and finite dispatch permits retain their two-second limits. Passive Capture/receipt transactions use a separate bounded five-second window for full encrypted-payload verification; they cannot issue a live capability. SQL statement/lock (two seconds) and SQL idle-transaction (five seconds) bounds remain unchanged. PREPARED recovery may restore exact missing physical chunks from the independent original; a clean committed operation still refuses an undeclared missing chunk rather than silently repairing it. These are explicit single-host operational bounds, not measured scale readiness or qualification of large UI/publication payloads.

## One financial transition

Capture reuses the original financial settlement transaction, journal, postings, evidence, disposition and outbox tables. It validates the existing SQL claim/witness, actual FDB admitted nonce and frozen Binding. It does not require a current execution grant or enabled current policy: already incurred expense must survive later revocation. This grants no further action or output permission. Known usage settles the actual frozen price once, including expense above a reservation; unknown usage retains the claim/hold and original evidence without inventing cost or release.

PREPARED binds the retained original's content address, exact evidence reference and financial before/after digests. SQL commits its evidence/financial rows and detector atomically. FDB commits the existing evidence value, a reference index, and exact detector/history afterward. The index is not another result or balance store. After capture, shared reconciliation acknowledges the existing evidence/settlement outbox through its own SQL-first transition. It cannot execute the unmanaged writer path.

| Retained state | Accounting recovery |
| --- | --- |
| Original only, no PREPARED | Derive normal capture work from the authenticated original and actual original admission |
| PREPARED, both previous | Retain/settle that exact incurred result after checking actual admission; never call the model |
| SQL next / FDB previous | Observe exact SQL witness/evidence/disposition; retain the same original FDB bytes and history |
| Both next or lost final ACK | Compare actual rows and original history; finish observation without another charge |
| SQL previous / FDB next | Refuse contradictory order; do not fabricate missing financial history |
| Clean markers but missing/changed actual evidence | Refuse; detector agreement does not authorize repairing an undeclared rollback |

The independent original's content hash and existing custody authentication both remain required. Missing/corrupt originals, exhausted profile capacity, unavailable independent staging plus unavailable fallback, pending negative resolution, and full SQL/FDB/cofre restore/takeover remain explicit operational work. No absence proves non-admission or refund.

## Incurred-result receipts

Shared ACKs use the existing `runtime_financial_acks` rows and FDB `financial` keys. A receipt refines its capture’s existing independent commitment with the sorted actual receipt kinds; it does not consume another subject or introduce another ledger. With no receipts the old pointer hash remains exact, so already retained captures preserve their prior commitments. ACK retries and recapturing the same ciphertext leave completed checkpoints unchanged.

Measurements of a maximum frame reached 1.36 s before the second complete payload verification, exhausting the old two-second small-operation budget. The five-second retention budget applies only to passive result/receipt paths; it does not extend dispatch permissions.

The original captured binding, SQL claim/admission witness, matching SQL/FDB ciphertext and actual outbox entry are required before acknowledging. Evidence ACK does not imply known usage: an unknown-cost hold remains held. Refund/release receipts stay unsupported until shared pre-dispatch release itself is qualified. ACKs do not authorize another provider call or publication.

PREPARED binds the exact record and previous/next financial and capture commitments. SQL-next/FDB-before must observe the actual original SQL ACK; a missing ACK under an advanced marker refuses. Both-previous can complete only the original declared receipt. Both-next verifies exact original history. FDB-next/SQL-previous, clean missing/altered references, and old actual SQL history hidden by current markers refuse; recovery does not invent another financial history.
