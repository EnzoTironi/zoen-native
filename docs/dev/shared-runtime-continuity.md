# Shared runtime continuity

## Shared runtime deployment

`RuntimeDeployment` and the `create_runtime`/`open_runtime` anchor constructors reuse the same durable prepare, history, consumption and generation locks for every principal in one SQL/FDB pairing. Namespace, witness and source identify this shared authority; the actual agent/device remains bound to each signed publication. A later effect by another agent advances the same checkpoint, and retirement drains effects from all principals. This is metadata for continuity, not a separate balance, device enrollment, financial admission or permission to publish.

The shared representation is schema 3, with distinct genesis/transition hash domains. Schema 2 remains byte-compatible and single-device scoped. Neither constructor adopts the other format or bootstraps missing state. An existing deployment needs an explicit authority migration; changing its schema or configuration is not a migration.

Relay's trusted operator file keeps its existing `devices` array and may also declare `runtimes`: each entry supplies `deployment` (`namespace`, `witness`, `source`), an absolute `anchor_directory`, and nonempty `principals` (`agent`, `device`). Several principals in that one entry share its reader. Duplicate devices, duplicate namespaces, mixed legacy/shared namespaces, wrong pairings and more than 256 total configured principals are refused. These locators do not replace the live directory, certificate, membership or per-effect managed-binding checks. No socket request can register a runtime or choose its anchor.

This shared anchor/relay contract is part of [general agent continuity #327](https://github.com/EnzoTironi/zoen-native/issues/327). The [reply execution contract](shared-reply-activation.md#public-reply-execution) qualifies native text calls and output with per-run authority. Construction alone grants no effect; complete isolated SQL/FDB/vault restore/takeover and absence-based financial release remain unqualified. Apps/creation work remains paused.

## Shared owner-policy continuity

`initialize_runtime_continuity(directory)` binds the actual SQL pairing and configured FDB source to a new private absolute anchor path. It accepts an unused execution namespace with no periods, policies or attempts; a missing anchor is never recreated over either existing detector. `open_runtime_continuity(directory)` opens the retained writer, verifies both actual checkpoints and the current policy inventory, and reconciles only an original retained signed policy. These APIs protect policy installation and native maintenance (bootstrap, retained MLS key packages, repack and source refresh); terminal wake consumption and financial restore qualification remain part of #327; reply execution/output need the separately qualified route. They do not set the runtime's production continuity Boolean or create a paid/output/refund capability.

The existing `runtime_image_checkpoint` table is reused, with profile 3 representing the shared scope and null legacy agent/device columns. Profile 2 remains device-scoped. No balance, ledger or policy store is duplicated. Legacy policy installation refuses a configured profile-3 row; native controls pass their original current-directory transaction into the shared installer. The same owner/month policy is shared across agents. Historical exact acknowledgements do not replace the latest version, clear disabled state or create financial effects.

Current subject hashes and the encrypted original policy intent are part of the anchor's atomic checkpoint rename. The next digest binds the complete subject-map hash, exact updates and encrypted intent. The original signed policy is retained in immutable checkpoint history. The independent directory contains hashes and ciphertext, not a plaintext policy copy. The cooperating single-host profile bounds metadata at 512 subjects, eight updates per checkpoint and 16,384 encoded intent bytes; exhaustion refuses before publication. This is an operational profile, not measured scale readiness.

Policy validation/staging uses the existing SQL implementation. Before either store changes, PREPARED retains the original signed request. The FDB transaction writes its exact checkpoint/history; the original SQL policy/directory transaction writes the policy and matching detector together; only matching actual store contents permit external COMMITTED. An interrupted policy install can replay that exact signed owner command with fresh owner-device, expiry and version checks. It never recovers a model/native execution permit.

| Retained state and actual stores | Policy recovery |
| --- | --- |
| PREPARED, both previous | Retain the original intent; forward that same valid policy, without resetting the checkpoint |
| PREPARED, FDB next / SQL previous | Verify original FDB history, reauthorize the same signed policy and advance its SQL transaction once |
| PREPARED, both next | Compare exact original history and the actual policy inventory, then commit the observation |
| PREPARED, SQL next / FDB previous | Refuse the contradictory order; do not fabricate missing FDB history |
| COMMITTED, old matching pair or rewound/missing policy rows | Refuse; agreement between old markers is insufficient |

A refused recovery retains its original evidence. The anchor must remain outside SQL/FDB/vault restore domains; privileged rollback of that directory, NFS and distributed writers are not covered by this single-host mechanism. Stop old executors and pin the same independent configuration at host entry points; an unconfigured/older binary over restored stores is not made safe by a marker in those stores. The complete takeover, native custody, external effects, incurred-cost and full-volume restore proof remains open under #327. Row-level failure cuts and automatic tests do not qualify that full operational contract or manual iPhone acceptance.

The automatic SQL restore case uses `pg_dump`/`pg_restore` into a new owned database; immutable-history triggers stay enabled. Overlaying only its mutable detector metadata must still refuse the older policy inventory. CI uses tools from its existing pinned PostgreSQL container (`ZOEN_TEST_PG_CONTAINER`); local fixtures use matching PostgreSQL tools on PATH. This SQL proof does not substitute for the remaining full FDB/vault/financial restore matrix. Deploy migration 0042 before the new runtime binary; it retains profile-2 defaults for existing deployments.

## Shared native maintenance

Native device roots join the existing policy subject map. Each commitment binds the exact authenticated capsule manifest, principal, generation and source cursor. Inventory reads use the existing bounded FoundationDB pagination helper; a partial range is not evidence of exceeding the bound. No second state store or financial ledger is introduced.

Maintenance retains the encrypted original activation intent before changing either detector. Its existing stage pin protects the original capsule from collection. The current certified directory transaction advances SQL first; one FoundationDB transaction activates that exact capsule, updates checkpoint/history and removes the pin. Recovery distinguishes this SQL-first native transition from the FDB-first policy transition. It never manufactures a replacement capsule or resets a checkpoint.

Cold recovery authenticates the original complete stage, takes a fresh device fence and current directory authorization, and completes only that retained activation. Later source entries are caught up afterward. An altered pin, missing/corrupted original material, missing vault key or valid old native root cannot substitute for the committed state. A crash before the pin was written can recover only from the independently retained intent and the exact original authenticated stage.

Automated real SQL/FDB tests cover bootstrap and source-refresh cuts before SQL, between SQL/FDB and after FDB, plus key-package publication/ACK, repack, cold reopen, missing vault key and old-root rollback. The current binary refuses native mutations without the configured shared writer before staging. Shared reply discovery retains its original run/wake batch and includes those actual effects in the same protocol. This does not qualify old binaries, full backup/takeover, paid output, refunds, measured scale or iPhone acceptance.

Shared reply discovery retains its exact encrypted batch through the existing chunked evidence codec. The prepared intent binds a reference to those original bytes. The final native activation transaction also writes the immutable run, prepared Binding, trigger dedupe, durable wake, GC reference and continuity index. Cold recovery replays that batch under fresh directory/device authorization; later source activity cannot replace its IDs or request. Another certified device observes the same trigger without creating another run.

The continuity index contains references to the originals, not a second queue. Reconciliation compares actual run/control-row hashes against those originals, so matching checkpoint markers cannot conceal a missing wake, Binding, run or index. Shared terminal wake consumption remains unqualified and must advance continuity before changing committed rows. Fresh reply execution uses the separately qualified route. The cooperating single-host profile bounds each retained discovery original at 3 MiB and the combined discovery inventory at 4 MiB, checked before prepare. These are explicit operational bounds, not measured production scale. Generic larger evidence reads keep their existing per-chunk transactions; shared inventory reads use the caller's coherent transaction. MLS claims use the shared exact-relay-clock codec, independently of monotonic event IDs; the server's future-operation refusal is unchanged.

## Durable stop requests

`cancel_model(run)` in a shared deployment retains the exact original cancellation request under the same checkpoint. The request binds the authenticated immutable run, attempt, record and Binding digests. It does not require the current execution grant, replace the original request, acquire worker leases, call a model or alter financial tables. Actual run and device leases remain valid; their old execution scope refuses the stop marker on revalidation.

The original encrypted stop intent is retained before the FoundationDB transaction writes the existing cancellation row, its continuity index and checkpoint/history together. SQL advances afterward. Recovery supports both previous, FDB-next/SQL-previous and both-next; SQL-next/FDB-previous contradicts this operation's order and is refused. The index only points to existing cancellation/run records; it is not a second queue. Missing or altered actual bytes cannot be repaired by resealing a replacement request. Exact replay and concurrent repeats observe the same original checkpoint.

The result stays `Requested`, including after restart or loss of the final acknowledgement. It is not confirmation that a worker/provider stopped, a proof of non-admission, terminal wake consumption or a financial release. Those transitions remain distinct; fresh reply/model output needs the qualified route; financial release stays closed. The durable wake is retained until its terminal operation is implemented. Apps/creation remain paused. Automated SQL/FDB failure cuts are separate from Enzo's pending product/device acceptance.

## Shared financial reservation

The existing reservation implementation accepts a caller-owned SQL transaction; its directory, latest signed policy, owner-wide limit, exact immutable Binding, closure gate, journal and postings remain authoritative. The normal admission session routes this phase through shared continuity when configured. A hold is not a fresh claim or provider permission. New provider calls also need the one-shot claim/witness and qualified reply route. Recovery alone grants none.

A financial subject hashes each nonempty owner/period's actual aggregate, attempts, claims, admission witnesses, evidence hashes, dispositions, journals, postings, outbox/ACKs and closure gates. Zero policy-created periods have no financial subject until an obligation or gate exists. No second balance or ledger is stored. Reads use bounded, ordered SQL metadata; large evidence is represented by PostgreSQL16 SHA-256 of the actual ciphertext. The cooperating profile bounds each source at 4,096 rows and combined financial metadata at 8 MiB. This is not measured scale readiness.

PREPARED retains the original encrypted reservation intent and financial before/after digests. SQL commits the original hold/journal/postings and checkpoint atomically; FoundationDB records the exact checkpoint/history afterward. Both-previous recovery requires actual native extraction, fresh paired leases, current source, directory, policy/budget and deadlines before creating the original hold. SQL-next recovery only observes that exact existing obligation; it cannot reconstruct a claim or send capability. FDB-next/SQL-previous contradicts this operation's order and is refused. A before-commit intent that can no longer be authorized remains refused/pending; automatic negative resolution and complete cancellation/release remain separate work.

Unannotated shared reserve/claim/dispatch-guard/settlement/release/outbox ACK mutations refuse before changing financial authority. Device-scoped Images behavior is preserved. New phase implementations must advance the same financial commitment before those operations can be enabled. Replaying an exact reservation adds no hold or checkpoint; a new attempt still sees every existing owner-wide obligation. A real older SQL backup, even with unchanged policies and advanced detector markers, must be refused against the current financial commitment. SQL backup evidence does not qualify full FDB/vault/financial deployment restore.

## Shared one-shot claims

Reservation and claim use the same financial transition routine and original SQL validation bodies. A live claim creates a fresh random nonce through the original uniqueness constraint, then atomically commits its SQL state/checkpoint before FDB history and external finalization. Only that live insertion can return the private non-cloneable claim after known successful commits. The normal admission session selects this path in shared mode; dispatch/settlement/output additionally require their own original permissions and qualified route.

The encrypted original claim intent retains the nonce, exact Binding and financial before/after digests under a distinct domain. Recovery may restore that exact nonce with fresh actual native authority when SQL is still previous, or observe the known original SQL claim. Neither branch returns a fresh claim object. Exact retry, cold reopen and lost ACK cannot turn stored nonce metadata into another authorization. A stop request retains the claim/hold; it does not prove non-admission or refund it.

Previous reservation intents retain their exact serialized bytes, hash domain and encryption subject when no claim is present. Automated format compatibility assertions cover this boundary. Real SQL/FDB tests cover five claim/ACK cuts, exact nonce retention, no fresh claim on cold retry, a real older SQL claim backup despite matching markers, and two actual workers contending for one run. Operational metadata bounds remain unchanged. Productive shared dispatch, terminal consumption, settlement/release, negative resolution and full deployment restore/takeover remain separate qualification work.


## Shared dispatch admission and send witness

The ordinary admission session selects the shared path when configured. Two separate checkpoints preserve the boundary between the original FDB admission and the SQL send witness. The first commits the existing admitted nonce, a reference to the immutable Binding, and FDB checkpoint/history atomically, then advances the SQL detector. Only known live completion returns a private, non-cloneable admission receipt. Recovery requires the actual FDB admission and matching history; it may advance a lagging SQL detector but cannot manufacture admission or return that receipt. Both-previous and contradictory SQL-first states refuse and retain pending evidence.

The receipt is consumed once by the existing financial transition routine. Its second checkpoint atomically commits the actual SQL witness and financial commitment, then advances FDB history. Current source, paired leases, directory, signed owner policy, budget, closure and grant deadline are revalidated. A known live SQL commit can create the ordinary finite send permit; its monotonic window includes SQL/FDB/finalization latency. The caller retains the existing generation guard through the admitted operation. Neither recovery nor stored nonce metadata can create that permit.

SQL-next witness recovery observes the original claim/witness and advances only missing detector/history. SQL-previous witness recovery refuses: a lost live receipt is not reconstructed from PREPARED. Before-commit negative resolution remains open; refusal preserves the financial hold rather than proving absence or refunding it. The dispatch index only references actual admitted/prepared rows, whose original bytes remain authoritative. Missing or altered admitted rows fail even when detector markers agree.

Automated cases cover normal live private permission and eight crash/ACK cuts, repeated cold observations, missing/mutated actual admission, and a real older SQL backup with the original claim but no witness despite advanced markers. They make no provider calls. Public native reply execution/capture/settlement uses the linked reply contract. Financial release, terminal wake consumption, negative resolution and complete deployment restore/takeover remain unqualified. These tests are not Enzo's product/device acceptance.

Incurred-result retention and accounting now have a shared implementation and automated service coverage; see [the capture contract](shared-runtime-capture.md). Retention alone grants no execution permission or complete restore qualification.

## Live reply route qualification

`qualify_shared_reply_output` resolves the current SQL/FDB pairing and complete native inventory under the existing shared anchor, retaining its generation lock. It validates every configured native credential against the actual certified SQL directory and actual relay sockets: the legacy handshake must be refused and the independently managed checkpoint binding must succeed. The same routing implementation serves Images and shared Runtime profiles. Relay selects the SQL checkpoint profile from its trusted anchor type; it cannot fall back to a device row for a shared runtime or accept a caller-selected profile.

The route remains bound to exact relay/source, configured principals and generation while normal checkpoints advance. A cold open does not deserialize route authority. This qualifies routing only: existing per-run directory, source/frontier, lease and native publication controls still apply, and shared reply activation now uses this same checkpoint; execution additionally needs native per-run admission; full continuity proof remains pending. Reply execution, delivery and receipts use the linked contract. WebSocket authentication may update normal reconnect metadata; qualification creates no attempt, model request, financial posting or publication.
