# ADR 0015: Staging runs on Fly.io (gru), with Cloudflare as the edge only

Status: accepted for the staging phase. Supersedes the provider choice in ADR 0012 until the
AWS migration; ADR 0012's seams (OpenTofu, container images, Kubernetes manifests) stay.

## Context
We need a real, reachable relay now, on Enzo's accounts, for little money. The domain is
`tryzoen.com` on Cloudflare; its root (and `app.`, `www.`, `auth.`) already serve other things
and are never touched. Fly is already logged in on the Mac. R2 is not enabled on the
Cloudflare account (API error 10042, it needs the dashboard and billing details).

## Decision
- **Cloudflare is the edge only**: DNS for `relay.`, `api.`, `media.` and `id.tryzoen.com`,
  managed by OpenTofu (`infra/tofu/envs/staging`, module `edge-dns`, which refuses the zone
  root). Records start DNS-only so Fly issues its own certificates; they move behind the proxy
  (`proxied = true`) once the zone's SSL mode is confirmed as Full (strict), because Flexible
  would loop against `force_https`. WebSockets work through the proxy.
- **Blobs go to Tigris** (S3-compatible, on the Fly bill, free tier 5 GB) through the relay's
  existing `object_store` S3 backend. R2 replaces it by changing four environment values once
  Enzo enables R2; blobs are ciphertext addressed by hash, so moving them is a copy.
- **Fly, region gru**, apps named `zoen-staging-*`, configs and the idempotent deploy script in
  `infra/fly/`:
  - `zoen-staging-relay`: the relay (sync WebSocket, blobs, apple-app-site-association),
    shared-cpu-1x 512 MB (the FoundationDB client adds its own thread and caches), one always-on machine (clients hold sockets open, so autostop would
    only add reconnects), `/metrics` on a private port scraped by Fly.
  - `zoen-staging-pg`: Postgres 17 on one machine with a 1 GB volume and daily snapshots,
    private network only. Self-run instead of Managed Postgres: $6/month against $38.
  - `zoen-staging-fdb` (S3): FoundationDB 7.3, one shared-cpu-1x 2 GB machine with a 2 GB
    volume and daily snapshots, `single` redundancy, private network only. The cluster file
    names the coordinator by DNS (`zoen-staging-fdb.internal:4500`), so a replaced machine
    doesn't strand clients. The three-machine `double` cluster first planned here would cost
    $33 of the $50 cap for a property staging doesn't need (surviving a host loss without the
    snapshot); production runs `double`/`triple` under fdb-operator (infra/k8s).
  - Later, when S5 (NATS bus) lands: `zoen-staging-nats`, one 256 MB machine with a 1 GB
    volume for JetStream. Not deployed before something uses it.
- Secrets are generated by the deploy script and go straight into `fly secrets`; the Postgres
  password never touches disk or logs.

## Alternatives
- **All-in on Cloudflare (Workers + Durable Objects).** A Durable Object per Space is a
  natural sequencer and fan-out point. Rejected: it means rewriting the Rust services for the
  Workers runtime and dropping FoundationDB; Cloudflare containers are stateless, so FDB
  can't run there, and the storage seam (ADR 0011) would collapse into one vendor's API.
- **Fly Managed Postgres.** Better operations, $38/month minimum; not worth it before there's
  data to protect. Revisit at the first external users.
- **AWS sa-east-1 now.** The long-term target (ADR 0012), but EKS alone is about $73/month
  before nodes, and no account or budget is approved yet.

## At 1B users
Staging says nothing about 1B by itself; it exists so the clients run against the same
binaries and protocol over the public internet. The production numbers stay in ADR 0008 and
cost-model.md. What carries over: images built from one Dockerfile per service, the OpenTofu
DNS module (the same records point at the AWS load balancer later), secrets never in git, and
region pinning (gru ≈ São Paulo, the first region in the multi-region plan).
